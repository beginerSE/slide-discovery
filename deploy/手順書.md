# 提案スライド検索 Cloud Run 移植・デプロイ手順書

本書は「提案スライド検索」(`artifacts/api-server` の FastAPI アプリ) を
Google Cloud Run へ移植・公開するための手順書です。英語版の詳細リファレンスは
同じディレクトリの `README.md` を参照してください。本書はそれを日本語で要約し、
コマンドを順番に並べた実務用のチェックリストです。

このアプリは GCP 本番モードでは **すべて ADC(Application Default Credentials)**
で認証します。Cloud Run に付与したサービスアカウントが、Cloud SQL・Vertex AI・
Drive API の認証情報を提供するため、**鍵ファイル(JSON キー)は一切作成・同梱しません**。

## ⚠️ 表記ルール:置き換える箇所

- **`《 》` で囲った部分は、必ずあなたの環境の値に置き換えてください**(例:
  `《プロジェクトID》` → `my-company-proj`)。`《 》` の記号ごと消して入力します。
- 下記の**サンプル名はそのまま使ってもOK**です(任意で変更可)。変える場合は
  **登場するすべての箇所をそろえて**変更してください:

  | サンプル名 | 用途 | 変更可否 |
  | --- | --- | --- |
  | `us-central1` | リージョン | 変更可(全箇所そろえる) |
  | `slide-search` | Artifact Registry のリポジトリ名 | 変更可(イメージ名と合わせる) |
  | `slide-search-session-secret` | Secret Manager のシークレット名 | 変更可(`session_secret_name` と合わせる) |
  | `slide-search-api` | Cloud Run のサービス名 | 変更可(`service_name` と合わせる) |
  | `github-conn` | Cloud Build の GitHub 接続名 | 変更可(トリガー作成時と合わせる) |
  | `slide-search-build` | Cloud Build トリガー名 | 変更可 |

- **あなたの環境ごとに必ず決める値**は次のとおりです:
  `《プロジェクトID》` / `《インスタンス名》`(Cloud SQL)/ `《接続名》`(= `《プロジェクトID》:us-central1:《インスタンス名》`)/ `《DB名》` /
  `《GitHubオーナー》`(GitHub のユーザー名または組織名)/ `《GitHubリポジトリ名》`。

## 構成ファイル

| ファイル | 役割 |
| --- | --- |
| `../Dockerfile` | FastAPI コンテナをビルド(uvicorn を `$PORT` で起動) |
| `../requirements.txt` | コンテナにインストールする Python 依存(ルート `pyproject.toml` と同期) |
| `../.dockerignore` | ビルドコンテキストから不要物(`data/`・`deploy/`・`*.md` 等)を除外 |
| `terraform/` | 本番環境の単一の正(API 有効化・SA・IAM ロール・Cloud SQL IAM ユーザー・Cloud Run サービス) |

開発(Replit)モードでは何も変わりません。`config.py` が環境変数で dev/gcp を
自動判定し、既定は dev です。

## 前提(初回のみ・運用者が手動で実施)

1. **課金が有効な GCP プロジェクト**と、`gcloud` CLI・`terraform` のインストール・認証:
   ```sh
   gcloud auth login
   gcloud auth application-default login
   gcloud config set project 《プロジェクトID》
   ```
2. **Cloud SQL(PostgreSQL)インスタンス**を作成しておく(`pgvector`・`pg_trgm`
   拡張は起動時に `db.py:init_db` が自動作成します)。接続名
   `《プロジェクトID》:us-central1:《インスタンス名》` を控えておきます。
3. **Artifact Registry の Docker リポジトリ**を作成:
   ```sh
   gcloud artifacts repositories create slide-search \
     --repository-format=docker --location=us-central1
   ```
4. **`SESSION_SECRET` を Secret Manager に作成**(全モードで必須):
   ```sh
   printf '%s' "$(openssl rand -hex 32)" | \
     gcloud secrets create slide-search-session-secret --data-file=-
   ```
5. **このソースコードを GitHub リポジトリに配置**しておく
   (`https://github.com/《GitHubオーナー》/《GitHubリポジトリ名》`)。
   Replit から直接 push できます(左の Git パネルで GitHub と連携 → コミット → push)。
   ビルドは次章のとおり **この GitHub リポジトリ経由**で行います。

## デプロイ手順

### 1. GitHub リポジトリからイメージをビルド(リポジトリ経由)

ローカルからの `gcloud builds submit` は使わず、**GitHub に置いたソースを
Cloud Build がビルド**して Artifact Registry に push します。`Dockerfile` は
`artifacts/api-server/Dockerfile` にあります。

**(1) Cloud Build と GitHub を接続**(初回のみ)。下記コマンド実行後に表示される
URL を開き、GitHub の Cloud Build アプリを承認して対象リポジトリへのアクセスを許可します:

```sh
gcloud builds connections create github github-conn --region=us-central1
# ↑ 表示URLでGitHubアプリを承認

gcloud builds repositories create 《GitHubリポジトリ名》 \
  --remote-uri=https://github.com/《GitHubオーナー》/《GitHubリポジトリ名》.git \
  --connection=github-conn --region=us-central1
```

**(2) ビルドトリガーを作成**(初回のみ)。`Dockerfile` を直接ビルドし、
`main` ブランチへの push で `:latest` イメージを Artifact Registry に push します:

```sh
gcloud builds triggers create github \
  --name=slide-search-build \
  --region=us-central1 \
  --repository=projects/《プロジェクトID》/locations/us-central1/connections/github-conn/repositories/《GitHubリポジトリ名》 \
  --branch-pattern='^main$' \
  --dockerfile=Dockerfile \
  --dockerfile-dir=artifacts/api-server \
  --dockerfile-image=us-central1-docker.pkg.dev/《プロジェクトID》/slide-search/api:latest
```

**(3) ビルドを実行**。`main` に push すると自動でビルドされます。手動で走らせる場合:

```sh
gcloud builds triggers run slide-search-build --branch=main --region=us-central1
```

> 以降は GitHub に push するたびに最新イメージが自動ビルドされます。新しい
> リビジョンを本番へ反映するには、ビルド完了後に次章 `terraform apply` を実行します。

### 2. Terraform で本番環境を構築

```sh
cd deploy/terraform
cp terraform.tfvars.example terraform.tfvars   # 下の表を見て値を編集する
terraform init
terraform apply \
  -var="image=us-central1-docker.pkg.dev/《プロジェクトID》/slide-search/api:latest"
```

`terraform.tfvars` の主な設定値(`《 》` は要置き換え):

| 変数 | 設定する値 |
| --- | --- |
| `project_id` | `《プロジェクトID》` |
| `region` | リージョン(既定 `us-central1`。Vertex AI の `GCP_LOCATION` も兼ねる) |
| `image` | プッシュ済みイメージ名 `us-central1-docker.pkg.dev/《プロジェクトID》/slide-search/api:latest` |
| `instance_connection_name` | Cloud SQL 接続名 `《プロジェクトID》:us-central1:《インスタンス名》` |
| `cloud_sql_instance_name` | `《インスタンス名》`(接続名の末尾部分) |
| `cloud_sql_db` | `《DB名》` |
| `create_cloud_sql_iam_user` | IAM 認証で DB 接続(鍵不要・GCP モード既定 `true`) |
| `session_secret_name` | `slide-search-session-secret`(手順4で作った名前) |
| `allow_unauthenticated` | 公開可否(アプリ自身がセッション認証を行うため既定 `true`) |

`terraform apply` は **サービス URL**・**サービスアカウントのメール**・
**Cloud SQL IAM ユーザー名**を出力します。以降の更新は **GitHub の `main` に push
→ Cloud Build が自動ビルド(手順1)→ `terraform apply`(本章)** の流れを繰り返すだけです
(`:latest` 固定のため `image` の指定は同じでOK。タグを毎回変えたい場合は `image` を更新)。

Terraform が自動で行うこと:
- 必要な API の有効化(run / sqladmin / aiplatform / drive / artifactregistry / cloudbuild)
- ランタイム用サービスアカウントの作成と IAM ロール付与
  (`cloudsql.client` / `cloudsql.instanceUser` / `aiplatform.user`)
- (任意)Cloud SQL の IAM データベースユーザー作成
- Cloud Run サービスの作成と GCP 用環境変数(`RUNTIME_ENV=gcp` ほか)の注入、
  `SESSION_SECRET` を Secret Manager から参照

## Cloud SQL 接続先の指定・変更方法

接続先はアプリのコードではなく**環境変数で決まります**(`db.py` が
`INSTANCE_CONNECTION_NAME` の有無で接続方式を切り替えます)。接続方式は
**Cloud SQL Python Connector**(Cloud SQL Admin API 経由)なので、Cloud Run へ
`--add-cloudsql-instances` を付ける必要はありません。

### 接続先を決める環境変数

| 環境変数(`terraform.tfvars` の変数) | 意味・指定値 |
| --- | --- |
| `INSTANCE_CONNECTION_NAME`(`instance_connection_name`) | 接続先インスタンス。形式は **`《プロジェクトID》:《リージョン》:《インスタンス名》`**(例 `my-proj:us-central1:slide-search-db`) |
| `CLOUD_SQL_DB`(`cloud_sql_db`) | データベース名 `《DB名》` |
| `CLOUD_SQL_USER`(`cloud_sql_user`) | DB ユーザー。**IAM 認証時は指定不要**(SA メールからドメインを除いた名前が自動採用)。パスワード認証時のみ指定 |
| `cloud_sql_instance_name`(Terraform 変数) | 接続名の**末尾のインスタンス名** `《インスタンス名》`。IAM DB ユーザー作成に使用 |
| `CLOUD_SQL_PRIVATE_IP`(`cloud_sql_private_ip`) | Private IP 接続なら `true`(VPC 接続が別途必要) |
| `CLOUD_SQL_PASSWORD` | パスワード認証時のみ。Secret Manager 推奨(`CLOUD_SQL_IAM_AUTH=false` と併用) |

> 接続名がわからない場合は、Cloud SQL のインスタンス詳細画面、または次のコマンドで確認できます:
> ```sh
> gcloud sql instances describe 《インスタンス名》 --format='value(connectionName)'
> ```

### 方法A:Terraform で変更(推奨)

`deploy/terraform/terraform.tfvars` を編集して再適用します。

```hcl
instance_connection_name = "《プロジェクトID》:《リージョン》:《インスタンス名》"
cloud_sql_instance_name  = "《インスタンス名》"   # 接続名の末尾
cloud_sql_db             = "《DB名》"             # 変わる場合
# プロジェクトごと変える場合は project_id も《プロジェクトID》に更新
```

```sh
cd deploy/terraform
terraform apply -var="image=us-central1-docker.pkg.dev/《プロジェクトID》/slide-search/api:latest"
```

Terraform が Cloud Run の環境変数を更新し、新インスタンス用の IAM DB ユーザーも
作り直します。

### 方法B:Cloud Run を直接更新(その場で素早く)

```sh
gcloud run services update slide-search-api --region us-central1 \
  --update-env-vars \
INSTANCE_CONNECTION_NAME=《プロジェクトID》:《リージョン》:《インスタンス名》,CLOUD_SQL_DB=《DB名》
```

> Terraform の state と差分(ドリフト)が出るため、恒久運用では方法Aに寄せてください。

### 接続先を変えるときの注意

- **権限の付与をやり直す**:新インスタンスでは IAM DB ユーザーに権限が無いので、
  次章「Cloud SQL の権限付与」の `GRANT`(+`CREATE ON SCHEMA`)を新DBで一度だけ実行。
- **拡張は自動**:`vector`/`pg_trgm` は起動時の `init_db` が作成(上記 `CREATE` 権限が前提)。
- **別プロジェクトへ移す場合**:そのプロジェクトで SA に `cloudsql.client` /
  `cloudsql.instanceUser` を付与し、`GCP_PROJECT` も変更。
- **リージョンは独立**:接続名のリージョンが変わっても Cloud Run のリージョンを
  合わせる必要はありません(コネクタはどのリージョンへも接続可)。

## 3. Cloud SQL の権限付与(IAM 認証の場合・初回のみ)

Terraform は IAM データベースユーザーを「**ログインのみ**」可能な状態で作成します。
テーブル権限は手動で付与する必要があります。管理者ユーザーで一度だけ接続し、
出力された `cloud_sql_iam_user`(= `《IAM DBユーザー名》`)に対して以下を実行してください
(`《IAM DBユーザー名》` は `terraform output cloud_sql_iam_user` で確認できます):

```sql
GRANT ALL ON ALL TABLES IN SCHEMA public TO "《IAM DBユーザー名》";
GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO "《IAM DBユーザー名》";
GRANT CREATE ON SCHEMA public TO "《IAM DBユーザー名》";  -- init_db が拡張/テーブルを作成
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT ALL ON TABLES TO "《IAM DBユーザー名》";
```

初回起動時に `init_db` が `vector`/`pg_trgm` 拡張・テーブル・インデックスを
作成するため、`CREATE` 権限が必要です。

> パスワード認証にする場合は `create_cloud_sql_iam_user = false` とし、
> `cloud_sql_user` を指定、`CLOUD_SQL_PASSWORD`(Secret Manager 経由)と
> `CLOUD_SQL_IAM_AUTH=false` を `extra_env` などで設定します。

## 4. Drive フォルダの共有(取り込み元がある場合)

GCP モードの Drive 取り込みは ADC(同じサービスアカウント)で Drive API を使います。
Drive の権限は IAM/Terraform では管理しません。通常のユーザーと同様に共有します:

1. `service_account_email` 出力のメールアドレス(= `《サービスアカウントのメール》`)を控える
   (`terraform output service_account_email` で確認)。
2. Google Drive で取り込み元フォルダ(または共有ドライブ)を開き、**共有**から
   その `《サービスアカウントのメール》` を **閲覧者(Viewer)** で追加する。
3. Drive API は Terraform が有効化済み。アプリは実行時に `drive.readonly` スコープを
   要求し、Google スライドは取り込み時に自動で PPTX へ書き出します。

## 5. 動作確認

```sh
curl -s "$(terraform output -raw service_url)/api/healthz" | jq
```

`/api/healthz` は解決済みの構成(シークレットは含まない)を返します。期待値:

```json
{
  "runtimeEnv": "gcp",
  "db": "cloud_sql",
  "cloudSqlIamAuth": true,
  "gemini": "vertex_ai",
  "drive": "drive_api"
}
```

値が想定と異なる場合は、対応する環境変数やロールが不足しています。ルート
`replit.md` の「GCP-native production」の対応表を確認してください。

## 補足・注意点

- **背景ジョブの常駐**: APScheduler による取り込み(1時間ごと)と埋め込み補完
  (5分ごと)を維持するため、Cloud Run は `min_instances = 1` かつ `cpu_idle = false`
  に設定しています(常時課金が発生します)。バッチ常駐が不要なら `min_instances = 0`
  に下げてコストを削減できますが、その間スケジューラは動きません。
- **依存の同期**: コンテナは `requirements.txt` をインストールします。ルートの
  `pyproject.toml`/`uv.lock` を変更したら `requirements.txt` も合わせて更新して
  ください(両者は同じ依存集合を表します)。
- **スキーマ管理**: DB スキーマは実行時に `db.py:init_db` が所有します。drizzle 等の
  外部マイグレーションは実行しないでください。
- **シークレットの取り扱い**: `terraform.tfvars` と鍵ファイルはコミットしないこと。
  `SESSION_SECRET` は必ず Secret Manager 経由で参照します。
